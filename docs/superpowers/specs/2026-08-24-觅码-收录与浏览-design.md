# 觅码 · 收录与浏览 设计文档

日期：2026-08-24 · 状态：已确认 · 需求来源：`觅码.txt`

## 1. 定位

觅码是 GitHub 之上的一层**曝光层 + 中文解读层**。代码永远留在 GitHub，觅码不托管、不 clone、不管权限，只存元数据、README、AI 解读结果与互动数据。

这条线是所有取舍的依据：任何需要存代码或管权限的方案一律出局。

两个目的有明确主次：

1. **第一目的（主路径）**：给想推广自己仓库的作者提供曝光途径 —— 主动投稿。
2. **第二目的（补充）**：丰富平台内容、发掘无名潜力创作者 —— 平台采集。

第二目的在不冲淡第一目的的前提下发展。

## 2. 项目拆分

原始构想含四个彼此独立的系统，逐块各走一轮 spec → plan → 实现。**本文档只覆盖第 1 块。**

| # | 子项目 | 范围 |
|---|---|---|
| **1** | **收录与浏览** | 投稿、采集、筛选、卡片流、仓库页、互动 |
| 2 | 仓库解读 | `Concept_Simplify` 移植进仓库页 |
| 3 | 曝光机制 | 行为数据积累后再引入推荐算法 |
| 4 | 变现 | 厂商 / 招聘视角 |

## 3. 架构

```
GitHub API
    │
    ├── [投稿]  OAuth → 勾选自己的仓库 → 编辑推广页 → 发布
    │
    └── [采集器] 定时轮询新仓库 → [筛选管道] 规则粗筛 → LLM 精筛
                                          │
                                          ▼
                    SQLite（元数据 + README + AI 结论 + 互动）
                                          │
[FastAPI] ◄───────────────────────────────┘
    │  ├─ /feed        规则排序的卡片流
    │  ├─ /repos/:id   仓库详情
    │  ├─ /files/*     GitHub API 文件代理 + 缓存
    │  ├─ /submit      投稿（OAuth owner 校验）
    │  └─ /me/*        收藏 / 历史 / 我的仓库
    ▼
[前端] React 18 + Vite + Zustand + TypeScript
    └─ 封面由前端 SVG 模版实时渲染，零图片存储
```

采集器与筛选管道是离线批处理，与 Web 请求完全解耦：前端故障不影响入库，采集故障不影响首页出内容。

技术栈沿用 `Concept_Simplify`（React 18 + Vite + Zustand + FastAPI），为第 2 块移植省一轮适配成本。MVP 用 SQLite，单机足够，扛不住再换 Postgres。

## 4. 两条入口，两套规则

采集端的门槛不是平台准入线。想推广的作者是第一目的，不应被「粉丝太多」或「项目太小」挡住。

| | 主动投稿（第一目的） | 平台采集（第二目的） |
|---|---|---|
| 谁发起 | 作者本人 | 平台 |
| followers < 500 | 不设 | 保留（发掘无名者的启发式） |
| star / 增速门槛 | 不设 | 保留 |
| LLM 评分 | **跑**，只影响排序 | 跑，兼作准入判定 |
| 能否发布 | 不设质量门 | 精筛不达标即丢弃 |
| 文案 | 作者自己写，LLM 只出草稿 | LLM 生成 |
| 封面 | 作者可上传，默认自动生成 | 自动生成 |
| 初始状态 | `published` | `pending_claim` |

`followers < 500` 是采集端的发掘启发式，不是准入线。

### 投稿门槛

只卡滥用底线：非本人 owner 的仓库、空仓库、恶意代码、违法内容。**不设质量门**。新人的第一个项目能发布、能拿到首发曝光窗口；点击率上不来则自然下沉。首页质量由排序把关，而非准入把关。

投稿同样跑一遍 LLM 精筛拿到 `quality` 评分，但该分**只参与排序，不作准入**：达不到分数的投稿照样能发布、照样进首发窗口，只是在窗口内排位靠后。这样优质投稿能凭分数拿到更高流量，粗糙投稿也不被拒之门外。副产品是投稿也拿到 `tagline_zh` 草稿，直接喂给「AI 帮我写」，省掉一次单独调用。

### 采集不冲淡投稿

采集日产出远高于投稿量，按分数混排会使投稿被概率性淹没，第一目的即失效。两个配置项解决，无需新代码：

- **采集日配额**：每天仅取分数最高的 30 条入库，不全量灌入。
- **首发加权窗口**：投稿仓库发布后 72 小时内排序加权 ×3，之后 ×1。
- **首页预留位**：见下节，为投稿保底曝光。

后者是觅码对作者的承诺：投了就有一波真实曝光。

### 投稿保底曝光

加权只能提高概率，不构成下限 —— 投稿多的那天照样有一半沉底。**下限只能靠预留位**，所以拆成两条通道，各管一件事：

- **加权（×3）**：让优质投稿在窗口内排得更前 —— 管「优质投稿流量更高」。
- **预留位**：首页每页固定留 `ceil(页容量 × 40%)` 个位置只给 72 小时内的投稿，按 `score` 从高到低填。填不满则回落给采集仓库，不留空位 —— 管「至少 50% 的投稿拿到保底曝光」。

**保底线的定义**：预留位里的投稿，其曝光量不低于当日采集仓库的曝光中位数。用预留位数量反推可保底的投稿数：预留位按日总曝光计算能覆盖 `M` 个投稿达到中位曝光量，若当日 72 小时窗口内投稿数 `> M`，则按 `score` 取前 `M` 个进预留位轮转 —— 优先保证高分投稿。

**当 M < 投稿数 × 50% 时**（投稿量涨上来了），说明预留比例不够，需上调预留位百分比。这是配置项，不是代码改动。

**验收**：一个日跑任务统计「72 小时窗口内投稿的曝光量分布」与「采集仓库曝光中位数」，输出达标比例。这个数掉到 50% 以下就是该上调预留比例的信号 —— 指标本身即监控，不额外建看板。

## 5. 投稿流程

投稿是核心产品面，是觅码给作者的推广工作台：

```
GitHub OAuth  →  勾选我的仓库（API 拉列表）  →  自动填元数据
                                                    │
                                                    ▼
        编辑推广页：一句话卖点 · 详细介绍 · 封面 · 分类标签
        （「AI 帮我写」：LLM 读 README 出草稿，作者可改）
                                                    │
                                                    ▼
                                                  发布
```

OAuth 顺带完成归属验证 —— 只能投自己 owner 的仓库，零人工审核，同时堵住外链刷量。

### 认领 = 同一条流程

认领不是独立功能：作者投稿时，若该仓库已被采集入库（`github_id` 命中），则复用原记录 —— `status` 转 `published`、`claimed_by` 置为该用户、LLM 生成的文案作为编辑页初值供其修改。作者由此接管自己的推广页，已积累的 star 数与互动数据不丢。

同一入口也提供**下架**（`status` → `delisted`）：不想被展示的作者一键退出，即合规底线里的 opt-out。

## 6. 采集与筛选管道

平台的质量闸门，也是唯一有真实运营成本的部分。

### 采集

每日轮询 GitHub Search API，查 `created:>=14天前 stars:>=3 fork:false`。Search API 单查询上限 1000 条，按语言分片绕过。每个候选仓库约需 3 次 core API 调用（README、文件树、作者 followers）；几百候选 ≈ 1500 次/天，认证配额 5000 次/小时，余量充足。

### 规则粗筛（零成本，几万 → 几百）

- README ≥ 500 字符；代码文件 ≥ 5 个；近 30 天有 commit；非 archived
- star 增速 ≥ 3/周（用增速而非绝对值，找的是刚起势的项目）
- 作者 followers < 500（把「给没名声的人曝光」编码进筛选，也是与 GitHub trending 的根本分野）
- 名称 / topics 黑名单：awesome、tutorial、homework、100-days、resume、dotfiles、leetcode

### LLM 精筛（每仓库 1 次调用，输入 README 前 4k + 文件树）

```json
{"is_real_project": true, "category": "开发工具",
 "tagline_zh": "给 LLM Agent 的最小运行时，200 行可读完",
 "why_zh": "把 Agent 循环剥到只剩必要部分，适合想搞懂原理的人",
 "quality": 4}
```

纯规则拦不住名称正常的课程作业与换皮项目，而这是最大噪声源；量降到几百后 LLM 成本可忽略。`tagline_zh` 同时供卡片与搜索使用 —— 把英文小项目讲给中文开发者听，是 GitHub 不做的事。复用 `Concept_Simplify` 的 `LLM_MOCK` 设计，离线亦可开发前端。

### 排序

```
score = 新鲜度 × 质量分 × (1 + 点击率) × 首发加权
```

`质量分` 对两条入口都取 LLM 精筛的 `quality`（投稿也跑精筛，只是不作准入）。因此优质投稿在首发窗口内排位更前，粗糙投稿仍能发布并占预留位，只是排在窗口末尾。72 小时后 `首发加权` 归 1，与采集仓库同台按点击率竞争。

LLM 精筛尚未跑完时 `quality` 取中性值 3，不阻塞发布（见错误处理）。

权重写在配置中，可手调。规则起步是因为冷启动无行为数据，双塔模型只会输出随机序；规则可解释、能手调，数据充足后进第 3 块 spec。

### 未认领仓库的合规底线

仅用官方 API；仅存元数据与 README；代码一律指向 GitHub 原链接；卡片标注来源；作者一键下架（opt-out）。成本为一个字段加一个接口。

## 7. 数据模型（4 张表）

```
users         github_id, login, avatar_url, bio(签名)
              └ 不存 access_token：登录用签名 cookie，投稿时走一次 OAuth
                （已登录 GitHub 即静默跳转），元数据刷新用平台 app token 拉公开信息

repos         GitHub 侧：github_id, full_name, owner_login, language,
              topics, stars, star_velocity, pushed_at, license, readme_md
              觅码侧：source(submitted|crawled), status(published|pending_claim|delisted),
              claimed_by, tagline_zh, intro_zh, category, cover_url(空=自动生成),
              quality, published_at, view_count, click_count

interactions  user_id, repo_id, kind(like|favorite|view), updated_at
              unique(user_id, repo_id, kind) + upsert
              └ 收藏夹 / 点赞 / 浏览历史 = 同表三个 where 查询，不是三张表

repos_fts     SQLite FTS5 虚拟表，索引 name + tagline_zh + intro_zh + topics
              └ 搜索零依赖，不引 ES / 向量库
```

分类是配置中的枚举，不建表。文件预览缓存用 `lru_cache`，不落库 —— GitHub 配额 5000/h 足够，量上来再换表。

## 8. 页面（5 个）

```
首页        顶栏：搜索 · 分类 tab · 浏览历史 · 用户菜单 · [推广我的仓库]
            卡片流：自动生成封面 + 标题 + 作者 + 时间，来源角标区分投稿/采集

仓库页      信息头（名称 · 卖点 · star · 语言 · 去 GitHub）
            switch 切换 ── 文件预览（树 + 代码，API 代理）
                        └─ 仓库解读（第 2 块 spec 填入）
            评论区：GitHub Discussions

投稿页      OAuth → 勾选我的仓库 → 编辑推广页（卖点/介绍/封面/分类，
            含「AI 帮我写」草稿）→ 发布

个人主页    签名（就地编辑）+ tab：我的仓库 / 收藏夹 / 浏览历史
```

### 封面

按主语言取色，SVG 模版实时渲染「色块 + 仓库名 + 技术栈标签」，零图片存储。一屏卡片因语言配色而有节奏感，扫一眼可分辨技术方向。作者认领或投稿后可上传自定义图替换。

### 互动

收藏 + 点赞在觅码本地（零 UGC 文本，零审核）；评论区挂 GitHub Discussions（类 giscus）。觅码带来的讨论直接落在开发者自己仓库里 —— 对作者是真实收益，也是认领的动机。

### 界面语言

界面中文，抓取全球仓库，AI 解读输出中文。

## 9. 错误处理

失败一律降级，不阻断：

- GitHub 限流/失败 → 采集器退避重试；单仓库失败跳过，不中断整批；文件预览失败显示「去 GitHub 查看」
- LLM 失败 → 采集侧精筛留在 pending 下轮重试；投稿侧**先发布**（`quality` 取中性值 3，照常进预留位与首发窗口），评分异步补齐后回填并重算 `score`。作者的发布动作永不因 LLM 故障被阻塞。
- 「AI 帮我写」失败 → 提示手写，不阻塞发布
- Discussions 未开启 → 显示「作者未开启讨论」，认领后引导开启

## 10. 测试

pytest 覆盖筛选管道（固定 fixture 喂规则判定）、排序公式含首发加权、**预留位填充逻辑**（投稿不足时回落给采集且不留空位、投稿超量时按 score 取前 M 个）、LLM 故障时投稿仍可发布、投稿归属校验；vitest 覆盖封面 SVG 渲染与卡片流。沿用 `Concept_Simplify` 的 `LLM_MOCK`，离线可跑全流程。

## 11. 刻意从简处

| 简化 | 何时补 |
|---|---|
| 不自建 git 托管 | 永不 —— 与定位冲突 |
| 无推荐算法，规则排序 | 行为数据充足后，第 3 块 spec |
| 预留位比例为固定配置，非自适应 | 达标比例长期掉到 50% 以下且手调频繁时 |
| 无设置页（只剩签名，就地编辑） | 出现第二个用户级配置项时 |
| 不存 GitHub token | 需后台代作者操作时 |
| SQLite + FTS5 | 单机扛不住时换 Postgres |
| 文件预览走 API 不 clone | 永不 —— clone 等于变相托管 |
