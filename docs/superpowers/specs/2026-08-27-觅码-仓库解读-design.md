### 2.2 新增（觅码特有）

- **`POST /api/repos/root`**：以仓库为根建图。后端拉取 GitHub 理解包（元信息/README/文件树/语言）→ 生成中心节点主题陈述 → 自动执行一次首层展开 → 一次性返回根 + 首层子节点 + 边。
- **仓库上下文注入**：会话内存住"仓库理解包"，后续所有 expand / detail / chat 的 prompt 追加仓库上下文块——子节点与解读必须贴合仓库实际模块与技术栈，不空谈通用知识。
- **自动建图流程**（前端）：进入 tab → 骨架屏 → 自动建会话 + 建根 + 首层展开 → 画布就绪。

### 2.3 移除

介绍页、`ConceptInputBox`、签名形变动画、四角灌木/八边形装饰、种子概念库（本来就没有）。

## 3. 架构

### 3.1 后端去向论证（决策 6）

**结论：新建 `backend/`（方案 1）不影响觅码平台正常运行**，理由：

1. 觅码目前**没有真实后端**——前端全走 mock client（`VITE_USE_MOCK` 默认开），新建独立服务不与任何现有运行时竞争；
2. 解读后端**不接觅码数据库**：它只吃前端传来的 `full_name` / `default_branch`（取自 `RepoDetail` 已有字段）并直调 GitHub API。与觅码主后端零耦合，纯属"同时跑两个进程"；
3. 开发期端口错开：觅码未来主后端规划为 8000（`vite.config.ts` 已有 `/api` → `:8000` 代理），解读后端用 **8100**，前端经 Vite 代理 `/explain-api` → `:8100`（重写为 `/api`）访问，无 CORS 问题；
4. 生产部署：静态前端 + 解读服务并存，反向代理把 `/explain-api` 转发到 8100 即可；未来觅码主后端上线后，二者可继续独立部署，也可合并（同为 FastAPI，解读服务按 APIRouter 组织可整体挂载）——两种路径都畅通，无需现在抉择。

### 3.2 系统数据流

```
觅码仓库页 RepoPage ──「仓库解读」tab
    │
    ▼
ExplainPanel（frontend/src/explain/）
    │  ① POST /explain-api/api/sessions          建会话
    │  ② POST /explain-api/api/repos/root        full_name + default_branch
    │        │
    │        ▼
    │  解读后端 backend/（FastAPI :8100）
    │        ├─ gh.py：GET /repos/{full_name}          （描述/默认分支）
    │        │        GET /repos/{full_name}/readme     （README，截 4000 字）
    │        │        GET /repos/{full_name}/git/trees…（文件树摘要）
    │        │        GET /repos/{full_name}/languages （语言统计）
    │        ├─ 会话内存住"仓库理解包"
    │        ├─ LangGraph：仓库主题陈述 → 拆解 → 关系描述（prompt 注入仓库上下文）
    │        └─ 返回 根节点 + 首层子节点 + 双向边
    │  ③ 画布渲染 d3-force 图
    │  ④ 用户点击节点 → POST /api/expand（带仓库上下文）
    │  ⑤ 双击节点   → POST /api/nodes/detail → 阅读器精读
    │  ⑥ 阅读器追问 → POST /api/reader/chat（NDJSON 流式 + Tavily）
    ▼
（设置区可随时覆盖单次展开数/最高层数/模型/Tavily，即时生效）
```

### 4.2 `gh.py` —— 仓库理解包

- 仅用 GitHub 官方只读 API；`GITHUB_TOKEN`（env，可选）用于提升限额，未配置时匿名访问（60 次/小时，够单机演示，不够生产）；
- 拉取：`GET /repos/{full_name}`（描述、默认分支）→ `GET /repos/{full_name}/readme`（raw，截 4000 字符）→ `GET /repos/{full_name}/git/trees/{branch}?recursive=1`（摘要：一级目录 + 文件计数，截 60 行）→ `GET /repos/{full_name}/languages`（语言占比）；
- 错误全部转 `GitHubFetchError`（用户可读文案）：404 → "仓库不存在或已私有"；403 → "GitHub API 限流…"；网络异常 → "GitHub 连接失败…"；
- 超时 10s；不缓存（每次进 tab 拉一次，量小；缓存留作后续扩展）。

### 4.3 仓库上下文注入

`prompts.py` 新增 `REPO_CONTEXT_BLOCK`（仓库简介/语言/目录概览/README 摘录 + "贴合仓库实情解释"纪律）与 `repo_block(repo)` 帮助函数；`DECOMPOSE_USER` / `RELATE_USER` / `ELABORATE_USER` / 阅读器 context 在原模板后**追加**该块（`repo_context` 为空时追加空串，通用行为不变）。原型的输出纪律（节点=概念陈述、箭头=两者区别、不合并同义）逐字保留。

### 4.4 会话与端点

- `_sessions[sid]` 增加 `repo_context: dict | None`，`/api/repos/root` 成功后写入；expand / detail / reader chat 从会话读取并透传给 graph 层；
- `POST /api/repos/root`：校验会话 → `gh.fetch_repo_context` → `run_repo_topic`（LLM 生成"XX 的解读"式主题陈述；mock 模式返回 `"{full_name} 仓库的解读"`）→ `run_expand(depth=0, repo_context=…)` → 组装 `RepoRootResponse{node, children, edges}`；
- 其余端点（sessions/roots/expand/nodes/detail/reader/chat/health）原样保留——通用概念入口 `/api/roots` 不删（保持与原型行为对齐，前端不使用）。

### 4.5 错误处理

| 场景 | 行为 |
|---|---|
| GitHub 限流/失败 | 502 + 可读文案，前端降级"解读服务暂不可用"卡（保留手动重试） |
| LLM 未配置 | 沿用原型 502 文案（提示设置区填模型） |
| LLM 输出两连败 | 沿用原型 RuntimeError → 502 |
| 会话过期（后端重启） | 沿用 404 "会话不存在或已过期"，前端整图重建 |
| 流中途异常 | 沿用 NDJSON `error` 事件收尾 |

## 6. 交互流程（用户视角）

1. 打开仓库页 → 切到「仓库解读」→ 骨架屏（后端拉 GitHub + LLM 生成，约 5–15s，mock 模式瞬时）；
2. 画布出现：中心节点 = "XX 仓库的解读"式主题陈述，外围一圈首层子节点（架构/核心模块/技术栈等，按相关度定大小）；
3. 点节点逐层深入；点边看双向关系气泡；双击节点开阅读器精读、可追问；
4. 右上工具栏：设置（单次展开数/最高层数/模型/Tavily）、练习模式（凭标题回忆）；
5. 全程不离开仓库页 tab；刷新/重进自动重开新会话（会话仅内存，与原型一致）。

## 8. 工程约定与从简处

- 裸色值：`theme.css` 之外**唯一例外**为 `explain-tokens.css`（节点色逐字迁移所需，spec §5.3）；
- 界面文案简体中文；解读组件 CSS 全部收在 `.explain-root` 作用域内；
- 每次提交只 add 本任务清单内路径（工作区存在他人未提交的首页改动）；
- 从简：GitHub 理解包不落库不缓存（每次进 tab 现拉）；会话仅进程内存（后端重启即失效，与原型一致）；不做按仓库的解读结果持久化——将来若做热门仓库预生成，另立 spec。
