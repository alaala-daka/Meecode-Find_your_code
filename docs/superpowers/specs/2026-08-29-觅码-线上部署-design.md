# 觅码 · 线上部署 设计文档

日期：2026-08-29 · 状态：待审批 · 上游依据：`2026-08-27-觅码-仓库解读-design.md`（§3.1 生产部署约定）· 需求来源：产品方部署需求沟通（2026-08-29）

## 1. 定位与目标

把觅码（静态前端 + 解读后端）部署到云服务器，通过 GitHub Actions 在 push 时自动部署，对外提供 HTTPS 访问。

### 1.1 产品方已确认的决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 部署架构 | **方案 A：CI 构建 + 服务器轻量运行**。前端在 GitHub Actions 内构建后 rsync 产物；后端在服务器 git pull + systemd 常驻。服务器不装 Node、不用 Docker |
| 2 | 部署触发 | push 到部署分支自动部署（GitHub Actions 以 SSH 密钥连服务器） |
| 3 | 访问方式 | 已有域名，启用 HTTPS（Let's Encrypt / certbot），80 端口 301 跳转 443 |
| 4 | 服务器现状 | Linux，已装 Nginx，无 Docker；只需补 Python venv 与 git 拉取 |
| 5 | 部署分支 | `feat/frontend-ui`（GitHub 当前默认分支）；若日后改名 main，改 workflow 触发分支即可 |
| 6 | 对外端口 | 仅 80/443；后端只监听 `127.0.0.1`，SSH(22) 保留管理 |

### 1.2 摸底事实（2026-08-29 核实）

- 仓库 `alaala-daka/Meecode-Find_your_code` 为 **public**，服务器可直接 HTTPS `git pull`，无需部署密钥。
- `backend/.env` 已被 `.gitignore` 正确忽略（仅 `.env.example` 入库），密钥未泄露。
- 后端仅一个 FastAPI 应用（`backend/app/main.py`，解读 API，含 `GET /api/health`）；信息流后端不存在，前端全走 mock。
- `frontend/src/api/client.ts:14` 在 `VITE_USE_MOCK=false` 时模块加载即抛错，会导致整站白屏（见 §3，必须先修）。

## 2. 总体架构

```
浏览器 ──HTTPS──▶ Nginx (80→301→443)
                   ├── /             → /var/www/meecode 静态文件（SPA 回退 index.html）
                   └── /explain-api/ → http://127.0.0.1:8100/api/（uvicorn, systemd 常驻）
                                     ▲
push feat/frontend-ui ─▶ GitHub Actions ──┤
                   ├── 前端：npm ci + build（VITE_USE_MOCK=false）→ rsync dist/ → /var/www/meecode
                   └── 后端：SSH → git pull --ff-only + pip install + systemctl restart
```

端口沿用仓库解读设计文档（§3.1）的约定：解读后端在 **8100**，为未来觅码主后端保留 8000（`vite.config.ts` 的 `/api` 代理目标）。Nginx 重写 `/explain-api/` → `/api/`，与 Vite 开发代理（`/explain-api` → `:8100`，重写为 `/api`）完全同构，前端代码零改动。

## 3. 前置代码修改（必须在部署前完成）

`frontend/src/api/client.ts`：删除 `VITE_USE_MOCK !== 'false'` 时抛错的分支，信息流**始终返回 mock client**，注释注明"信息流真实后端就绪后在此接 fetch('/api/...')"。

- 依据：信息流后端不存在（仓库解读设计文档 §3.1 第 1 条），`VITE_USE_MOCK` 的真实语义此后只服务"仓库解读"客户端（`explain/api/client.ts` 按调用时机判定，逻辑不变，相关测试不受影响）。
- 生产构建设 `VITE_USE_MOCK=false`：解读走真实后端，信息流继续 mock 数据，整站可正常加载。

## 4. 服务器布局与进程管理

```
/opt/meecode/              # git clone（public 仓库，HTTPS 拉取）
  backend/.env             # LLM_API_KEY、TAVILY_API_KEY、GITHUB_TOKEN 等，一次性手工创建，永不进 git
  backend/.venv/           # Python 虚拟环境（python3 -m venv）
/var/www/meecode/          # 前端 dist 产物（CI rsync --delete 覆盖）
```

- systemd 服务 `meecode-backend.service`：
  - `ExecStart=/opt/meecode/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8100`
  - `WorkingDirectory=/opt/meecode/backend`（保证 `config.load_dotenv()` 读到 `.env`）
  - **单 worker**：会话存进程内存（`_sessions` dict），多 worker 会串会话
  - `Restart=always`、`User=` 专用低权用户（如 `deploy`）

## 5. Nginx 与 HTTPS

- `80`：`return 301 https://$host$request_uri;`
- `443 ssl`：证书由 `certbot --nginx -d <域名>` 签发并自动续期。
- `location /`：`root /var/www/meecode; try_files $uri $uri/ /index.html;`（react-router SPA 回退）。
- `location /explain-api/`：
  - `proxy_pass http://127.0.0.1:8100/api/;`（尾斜杠完成前缀替换）
  - `proxy_http_version 1.1; proxy_set_header Connection "";`
  - `proxy_buffering off;`（伴读追问是 NDJSON 流式响应，禁止缓冲）
  - `proxy_read_timeout 300s;`（LLM 慢响应）
- `/api` 不配置：信息流无真实后端，未命中即走 SPA 回退。

## 6. GitHub Actions 工作流

新增 `.github/workflows/deploy.yml`，单 job，`push` 到 `feat/frontend-ui` 触发（paths 过滤：仅 `frontend/**`、`backend/**`、workflow 自身变更时部署，纯 docs 改动不部署）：

1. `actions/checkout@v4` + `actions/setup-node@v4`（Node 20，npm 缓存）
2. `npm ci && npm run build`，环境变量 `VITE_USE_MOCK=false`
3. rsync `frontend/dist/` → 服务器 `/var/www/meecode/`（`--delete`）
4. SSH 执行（`&&` 串联，任一步失败即中止，旧版本继续在线）：
   `cd /opt/meecode && git pull --ff-only && backend/.venv/bin/pip install -r backend/requirements.txt && sudo systemctl restart meecode-backend`
5. 部署后健康检查：`curl -fsS https://<域名>/explain-api/health`（后端 `GET /api/health` 经 Nginx 重写），失败则 workflow 标红

**GitHub Secrets（3 个）**：`SSH_HOST`（`user@服务器IP`）、`SSH_PRIVATE_KEY`（服务器上新生成的专用 ed25519 deploy key 私钥）、`DEPLOY_DOMAIN`。

## 7. 一次性初始化 runbook

写成 `docs/deploy-runbook.md` 随仓库提交，按序覆盖：

1. 服务器：创建 `deploy` 低权用户 → 安装 `python3-venv` → `git clone` 仓库到 `/opt/meecode`
2. 后端：建 venv → `pip install -r requirements.txt` → 手工编写 `backend/.env`（密钥从本机 `.env` 迁移）
3. deploy key：`ssh-keygen -t ed25519` 生成专用密钥对，公钥入 `authorized_keys`
4. systemd：安装 `meecode-backend.service` → `enable --now` → `curl 127.0.0.1:8100/api/health` 验证
5. Nginx：放置站点配置 → `nginx -t && reload` → certbot 签证书
6. GitHub：配置 3 个 Secrets → 手动触发/推送一次验证全链路

## 8. 失败处理与回滚

- 部署链 `&&` 串联：git pull 冲突（`--ff-only` 失败）、pip 安装失败、重启失败均中止部署，线上旧版本不受影响。
- 前端 rsync `--delete` 存在秒级新旧文件混合窗口，单机规模可接受，不做原子符号链接切换（YAGNI）。
- 回滚（runbook 写明）：服务器 `git checkout <旧commit>` + 重启 systemd；前端用 CI 重发旧 dist（对旧 commit 手动 Run workflow 或本地构建 rsync）。
- 健康检查失败 → workflow 标红 + GitHub 邮件通知，按回滚步骤处理。

## 9. 验证清单

- 本地：`pytest`（backend）、`vitest run` + `npm run build`（`VITE_USE_MOCK=false`）全部通过。
- 线上：`https://<域名>/explain-api/health` 返回 `{"ok": true}`；首页 200；SPA 深链接刷新不 404；仓库解读 tab 完成一次自动建图 + 伴读追问真实流式回答；`systemctl status meecode-backend` 正常、服务器重启后自愈。
